让发版自己发生

一个只有十九个文件的仓库，没有构建步骤，也没有依赖。但它有两条流水线： 一条在每次提交时说不，一条在打标签时把包做好。

作者 ShirakawaFM 约 2600 字 GitHub Actions · 静态文件

发布一个浏览器扩展，本来只需要三步：改版本号、压缩文件夹、上传到 Release。 手动做过几次之后，我发现每次都会在某个环节出错，而且错法几乎是一样的。

手动发版的三个漏洞

  • 版本漂移：改了 manifest.json，忘了改 README 徽章，或者反过来；
  • 包内旧文件：压缩时顺手把工作目录打进去，包里的内容和你以为的不一样；
  • 忘记附件：Release 写完了，但 zip 没传，用户点下载发现是空的。

这三件事都不难防，难的是每次都记得。于是我把它们交给流水线：能自动判断的，不再靠人。

两个工作流，两种职责

.github/workflows/validate.yml 在每次推送和 PR 时运行，只做检查，不产物：

  • 解析 manifest.json，确认 manifest_version 是 3、版本号格式合法；
  • 遍历 manifest 引用的每个文件，确认它们真的存在；
  • 对每个 .js 跑 node --check；
  • 检查 popup.html 里的本地资源路径；
  • 确认仓库里没有提交 zip / crx / pem。

最后一条看起来小题大做，但它最有价值：打包产物一旦进仓库，历史里就永远多出几 MB， 而 GitHub 的单文件上限是 100 MB——踩到一次就很难看。

版本守卫：让 tag 与文件互相证明

release.yml 只在推送 v* 标签时运行。第一步不是打包，而是拒绝： 

TAG="${GITHUB_REF_NAME#v}"
MANIFEST_VERSION="$(node -p "require('./manifest.json').version")"
if [ "$TAG" != "$MANIFEST_VERSION" ]; then
  echo "::error::Tag v${TAG} does not match manifest ${MANIFEST_VERSION}"
  exit 1
fi

这条判断消灭了「tag 是 v2.4.4、包内还是 2.4.3」的问题。它也有一个副作用： 如果你先打标签、后改版本号，工作流会失败。这个副作用是好的——版本号必须在打标签之前就确定， 而不是在失败之后补。

只打包该打包的

扩展的运行时文件只有五个：manifest.json、content.js、 popup.html、popup.css、popup.js。 文档和许可证可以带上，但 .git、docs/、node_modules/ 不该进包。 

mkdir -p dist/douyin-auto-hd
cp manifest.json content.js popup.html popup.css popup.js dist/douyin-auto-hd/
cp README.md README_EN.md LICENSE CHANGELOG.md dist/douyin-auto-hd/
(cd dist && zip -r -9 "douyin-auto-hd-v${VERSION}.zip" douyin-auto-hd > /dev/null)
(cd dist && sha256sum "douyin-auto-hd-v${VERSION}.zip" > SHA256SUMS.txt)

关键是 zip 的根目录结构：manifest.json 必须位于压缩包第一层， 这样用户解压后可以直接在 chrome://extensions/ 里选文件夹。 如果多包一层目录，很多人会选错层级，然后看到「清单文件缺失」。

在本地预演流水线

Actions 的反馈通常要等几十秒，调试起来很慢。Git for Windows 自带 Git Bash， 可以先把工作流里的 run 脚本抽出来，在本地真实执行一遍。 

import yaml, pathlib
data = yaml.safe_load(pathlib.Path(".github/workflows/validate.yml").read_text())
for job in data["jobs"].values():
    for step in job["steps"]:
        if "run" in step:
            print(step["name"], "→", len(step["run"]), "chars")

把脚本拼成一个 shell 文件，用 bash 跑。这比读一遍 YAML 可靠得多： 它会真实地暴露路径错误、变量未定义、以及「本地能过、runner 上不能过」的差异。 这套做法后来也成了我改工作流的标准流程。

三个真实的坑

1. tag 打在了错误的提交上

第一次发版时，我先提交代码再打标签，中间又补了一个文档提交。结果 tag 指向旧提交， Release 里的 README 还是上一版。教训不是「别改文档」，而是发版顺序要固定： 先确定提交、再打标签、最后推送 tag。

2. Git 不走系统代理

浏览器能打开 GitHub，git push 却报 Recv failure: Connection was reset。 原因是 Clash 的系统代理只对浏览器生效，Git 默认直连。给单次命令加代理即可： 

git -c http.proxy=http://127.0.0.1:7890 push origin main

3. Actions 没有写权限

工作流在创建 Release 时报 Resource not accessible by integration。 需要在 Settings → Actions → General 里把 Workflow permissions 改成 Read and write。这个设置默认是只读的，第一次发版几乎必踩。

发布的成本决定发布频率

流水线本身不产出功能，但它改变了一个更重要的东西：发版的边际成本。 当发布只需要 git tag 和一次推送，你会更愿意发小版本，而不是攒一个大的。 小版本意味着更小的变更面、更容易回滚、更少的「这次改了太多」。

现在这个仓库的发布流程是：改版本号、写 CHANGELOG、提交、打标签、推送。 剩下的事情——校验、打包、算 SHA-256、创建 Release——都不需要我看着。
